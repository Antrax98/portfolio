= portfolio
:toc: macro
:toclevels: 2
:source-highlighter: highlight.js

Portafolio personal de una sola persona: una página pública con la presentación
del dueño y sus proyectos, y un panel privado desde el que él mismo lo edita
todo.

Está partido en dos aplicaciones que se despliegan por separado:

[cols="1,3"]
|===
| `apps/nest-backend` | API en NestJS con arquitectura hexagonal y DDD, Postgres vía TypeORM y OpenAPI.
| `apps/next-frontend` | Next.js con MUI. El token vive en una cookie `httpOnly` que pone el propio Next, nunca en el navegador.
|===

No hay workspace de pnpm: cada aplicación instala y compila lo suyo, para que
cada una pueda construir su imagen con su propio contexto.

toc::[]

== Requisitos

* *Node* 22 o superior (`node -v`).
* *pnpm* — `corepack enable pnpm` si no lo tienes.
* *Docker* con `docker compose`, solo para levantar Postgres en desarrollo.

== Puesta en marcha

El orden importa: el frontend no compila sin los tipos que se generan del
backend, así que el backend va primero.

=== 1. El backend

[source,bash]
----
cd apps/nest-backend
pnpm install
cp .env.example .env
----

Rellena el `.env`. Para desarrollo local sirve esto tal cual:

[source,ini]
----
DB_HOST=localhost
DB_PORT=5432
DB_USER=portfolio
DB_PASS=portfolio
DB_NAME=portfolio

PORT=8080
NODE_ENV=development

JWT_SECRET=cambia-esto-por-algo-largo-y-aleatorio
JWT_EXPIRES_IN=1h

ADMINER_PORT=8081
----

WARNING: El `JWT_SECRET` de producción tiene que ser otro, y generado al azar:
`openssl rand -base64 48`.

Levanta la base de datos. El `compose.yml` trae Postgres y Adminer, nada más —
las dos aplicaciones corren fuera de Docker en desarrollo:

[source,bash]
----
docker compose up -d
----

Crea el esquema. `synchronize` está en `false` a propósito, así que las tablas
salen de las migraciones y no de las entidades:

[source,bash]
----
pnpm migration:run
----

Y arranca:

[source,bash]
----
pnpm start:dev
----

La API queda en `http://localhost:8080` y la documentación de OpenAPI en
http://localhost:8080/api[localhost:8080/api], con el JSON en `/api-json`.

=== 2. La primera cuenta

La base arranca vacía y el portafolio no sirve de nada sin dueño. Con el backend
y el frontend levantados, entra a `http://localhost:3000`: al no haber ninguna
cuenta te redirige a `/setup`, que es un formulario de registro. Al enviarlo se
crea la cuenta, se inicia sesión y caes directo en el panel.

Ese registro *se cierra solo*: en cuanto existe una credencial el endpoint
devuelve 409 y `/setup` deja de ser accesible. No hay forma de dar de alta a un
segundo usuario sin tocar la base de datos, y es a propósito — el portafolio es
de una sola persona.

Si prefieres hacerlo sin navegador:

[source,bash]
----
curl -X POST http://localhost:8080/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"tu-usuario","email":"tu@correo.com","password":"tu-contraseña"}'
----

NOTE: Para entrar sirven tanto el correo como el nombre de usuario, y ninguno
distingue mayúsculas de minúsculas. El campo del DTO se llama `identifier`
justamente porque el backend no sabe cuál de los dos le estás mandando.

=== 3. El frontend

[source,bash]
----
cd apps/next-frontend
pnpm install
cp .env.example .env
----

El `.env.example` ya trae el valor bueno para desarrollo
(`BACKEND_URL=http://localhost:8080`).

[source,bash]
----
pnpm dev
----

Queda en `http://localhost:3000`. La página pública es `/`, el panel
`/dashboard` y se entra por `/login` con la cuenta del paso 2.

== Los tipos del API

`lib/api/generated.ts` se genera del spec de OpenAPI y *está versionado a
propósito*: si no lo estuviera, nadie podría compilar el frontend sin levantar
antes Postgres y el backend.

Hay que regenerarlo a mano cada vez que cambie un DTO o una ruta, *con el backend
levantado*:

[source,bash]
----
cd apps/next-frontend
pnpm gen:api
----

IMPORTANT: Este es el único punto donde las dos aplicaciones están acopladas, y
es la razón de que vivan en el mismo repositorio: así el cambio en el DTO y el
`generated.ts` que lo refleja caben en un solo commit y se revisan juntos.

== Scripts

.`apps/nest-backend`
[cols="1,2"]
|===
| `pnpm start:dev` | Arranca en modo watch.
| `pnpm build` / `pnpm start:prod` | Compila a `dist/` y lo ejecuta.
| `pnpm migration:generate src/migrations/NombreDelCambio` | Genera una migración comparando entidades contra la base.
| `pnpm migration:run` / `pnpm migration:revert` | Aplica o deshace.
| `pnpm lint` | oxlint sobre `src/` y `test/`.
|===

.`apps/next-frontend`
[cols="1,2"]
|===
| `pnpm dev` | Servidor de desarrollo.
| `pnpm build` / `pnpm start` | Compila y sirve la versión de producción.
| `pnpm gen:api` | Regenera los tipos desde el backend levantado.
| `pnpm format` | Prettier sobre todo el proyecto.
|===

== Convención de commits

`lefthook` y `commitlint` viven en la raíz y cubren los dos lados del monorepo.
Se instalan solos con el `pnpm install` de la raíz:

[source,bash]
----
pnpm install
----

Los mensajes siguen
https://www.conventionalcommits.org/[Conventional Commits]; el cuerpo no puede
pasar de 100 caracteres por línea.

== Limitaciones conocidas

Dos cosas que se notan nada más clonar, y que están pendientes a propósito:

* *Los tests no corren.* TypeScript 7 exige `rootDir` explícito, y resuelto eso
  Jest 30 necesita Node ≥ 24.9 para cargar NestJS 12, que es ESM puro. Todo lo
  verificado hasta ahora se hizo levantando la aplicación.
* *El lint del frontend está roto.* `typescript-eslint` 8.70 no soporta
  TypeScript 7.0.2 y `pnpm lint` falla sin llegar a analizar nada.
